# Deployment

**Status:** as built on 2026-11-15. Live at
<https://steve-m365.github.io/apple-price-au/>, Pages source GitHub Actions
(`build_type: workflow`), first deploy `43705509182` green, variable
`PUBLIC_SITE_URL` set to the project URL. This page is the as-built record.

## 1. What actually deploys

`deploy-site` builds `site/` with Astro (`npm run build`), uploads `site/dist/`
via `actions/upload-pages-artifact@v3`, and publishes that artefact via
`actions/deploy-pages@v4`. There is no `gh-pages` branch, no branch-based deploy
and no server at runtime.

The build emits `/`, `/404.html`, `/robots.txt`, `/sitemap-index.xml`,
`/sitemap-0.xml` and `/_astro/*`. `robots.txt` is generated by
`site/src/pages/robots.txt.ts`; sitemaps by `@astrojs/sitemap`. As a project page,
URLs carry the `/apple-price-au/` prefix from `base` in `astro.config.mjs`, not by
hand.

## 2. The gate

`validate` runs the gate, `build` needs `validate`, and `deploy` needs `build`:

```bash
uv sync --locked
uv run python -m scripts.validation.validate_data
```

A hard failure exits non-zero, fails `validate`, and `needs: validate` stops the
build and deploy. **This is currently the only gate in the deploy path.** The
deploy workflow runs that validation itself; it does not wait for a separate
`validate-data.yml` run. It runs without `--strict` while `config/validation.yml`
sets `require_adapter_modules: false`; APA-030 flips both. Warnings do not block;
hard failures do.

## 3. Triggers

| Trigger | Condition |
|---|---|
| `push` to `main` | changes under `site/**`, `data/**`, `config/**` or `.github/workflows/deploy-site.yml` |
| `workflow_dispatch` | manual run from the Actions tab or `gh workflow run` |

A data-only or config-only push runs **both** workflows as separate runs, and
neither waits. `scripts/**` or `tests/**` alone runs only `validate-data.yml`;
automatic deploys come only from `main`, and pull requests and tags do not deploy.

## 4. Configuration: `PUBLIC_SITE_URL`

The workflow reads repository variable `PUBLIC_SITE_URL`; `astro.config.mjs` maps
its origin to `site` and its path to `base`. The project URL
`https://steve-m365.github.io/apple-price-au` gives site
`https://steve-m365.github.io` with base `/apple-price-au/`; a root URL gives base `/`.

Astro prefixes asset and internal links with `base`; canonical and sitemap URLs
use `site` plus `base`. A wrong path — omitted, misspelt, or left over after a
domain change — points links at the wrong root and makes assets 404 under the
served subpath.

Use the real deployment address; `example.com` below is a placeholder:

```bash
gh variable set PUBLIC_SITE_URL --repo Steve-M365/apple-price-au --body "https://example.com"
gh workflow run deploy-site.yml --repo Steve-M365/apple-price-au --ref main
```

Changing the variable does not redeploy; `robots.txt` follows the build URL.

## 5. First-time setup on a fresh repository

From the repository root, create the repository, enable Pages, set the variable,
then run the workflow:

```bash
gh repo create Steve-M365/apple-price-au --public --source=. --remote=origin --push
gh api -X POST /repos/Steve-M365/apple-price-au/pages -f build_type=workflow
gh variable set PUBLIC_SITE_URL --repo Steve-M365/apple-price-au --body "https://steve-m365.github.io/apple-price-au"
gh workflow run deploy-site.yml --repo Steve-M365/apple-price-au --ref main
```

Confirm with `gh api /repos/Steve-M365/apple-price-au/pages --jq '.build_type'`
(`workflow`). If already enabled, `POST` fails; use `gh api -X PUT
/repos/Steve-M365/apple-price-au/pages -f build_type=workflow`. Pages must exist
before the first deploy: `configure-pages` reads it in the build job, so enabling
it later means rerunning.

## 6. Rollback

Production is whatever `main` last deployed. Revert and redeploy:

```bash
git revert <sha>
git push origin main
```

A revert touching `site/**`, `data/**`, `config/**` or the deploy workflow
triggers `deploy-site`; otherwise run it manually. Pages keeps the previous
deployment live until success, so a failed run does not take the site down.

## 9. Custom domain, when it happens

No custom domain is configured (`cname: null` on 2026-11-15); adding one drops
the project path.

| Record | Name | Value |
|---|---|---|
| `A` | apex (`@`) | `185.199.108.153`, `185.199.109.153`, `185.199.110.153`, `185.199.111.153` |
| `AAAA` | apex (`@`) | `2606:50c0:8000::153`, `2606:50c0:8001::153`, `2606:50c0:8002::153`, `2606:50c0:8003::153` |
| `CNAME` | `www`, or another subdomain | `steve-m365.github.io` |

Set the custom domain (`CNAME`) in **Settings → Pages → Custom domain**, not
with a repository `CNAME` file; under Actions, that setting is authoritative.

Then set the variable to the root URL and redeploy:

```bash
gh variable set PUBLIC_SITE_URL --repo Steve-M365/apple-price-au --body "https://prices.example.com"
gh workflow run deploy-site.yml --repo Steve-M365/apple-price-au --ref main
```

A root URL makes `base` `/` and moves assets from `/apple-price-au/_astro/` to
`/_astro/`. If the old path stays, canonical links, the sitemap and assets still
point under `/apple-price-au/` while Pages serves the domain at `/`, so they 404.
After DNS resolves, run the section 7 checks, then enable **Enforce HTTPS**.
